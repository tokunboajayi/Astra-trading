# Onboarding: how this codebase works

Written for a developer who knows **Python, HTML and JavaScript**. That is exactly this
stack — there is no TypeScript, no React, no build step, no bundler, no `node_modules`.
If you can read a Flask app and a `document.getElementById`, you can read all of this.

**Total size: about 4,000 lines.** You can genuinely read the whole thing in an afternoon.

---

## 1. The one-sentence version

> A Python server holds all the truth about a fake stock-trading session. The browser asks
> it for a picture of the world, draws that picture, and sends back what the user clicked.

That's it. Everything below is detail.

---

## 2. The one rule that explains every design decision

**The browser never calculates anything about money.**

Not the price, not the fill, not the profit, not the loss. If you catch yourself writing
`price * quantity` in a `.js` file, stop — that number should have come from the server.

Why: if the browser could compute a fill, the browser could be wrong (or cheated), and the
screen would disagree with the server. So the server does the maths and sends the answer.

In practice this means every button click follows the same loop:

```
click  →  POST /api/something  →  server recalculates EVERYTHING
       →  server returns the complete new state
       →  browser throws away what it had and redraws from that
```

There is no partial update anywhere. No "just change this one number on screen."

## 3. Read the files in this order

Don't read alphabetically. Read in this order and each file will explain the next.

### Step 1 — `server/sim_engine.py` (182 lines) — **start here**

Pure maths. No web framework, no database, no file reading, no randomness, no clock.
Every function takes plain numbers and dicts and returns plain numbers and dicts.

You can run it in a REPL with no server:

```bash
python -c "from server import sim_engine as s; print(s.apply_fill(10000, None, 'BUY', 10, 168.0))"
```

Read these four functions and you understand the whole simulation:

| Function | What it answers |
|---|---|
| `apply_fill()` | "I bought 10 shares — what's my new cash and position?" |
| `check_open_orders_for_bar()` | "Did any waiting order trigger on this day?" |
| `check_safety_net_candidates()` | "Is anything down 8% and unprotected?" |
| `shadow_delta()` | "What if I'd ignored the safety net and held?" |

Everything in this file has a docstring. **11 of 13 functions are documented** — it is the
best-explained file in the repo, which is why it's first.

### Step 2 — `fixtures/HLX.json` — the fake market

Just data. 90 days of `{day, o, h, l, c}` — open, high, low, close. No dates (a real date
would imply real history), no volume.

The prices are **invented**, generated by `scripts/build_fixtures.py`, and every file says
`"synthetic": true`. They're built deliberately so the demo always hits the same numbers.

Open the file. Scroll it. It will take 30 seconds and demystify a lot.

### Step 3 — `server/main.py` (612 lines) — the web layer

This is the biggest file, but it's mostly repetitive in a good way. Read it in three passes:

**Pass 1 — the `Session` dataclass (~line 72).** One object holding the entire state of one
user's session: cash, positions, orders, which day they're on. Read the field names and
their comments. This is the vocabulary for everything else.

**Pass 2 — `snapshot()` (~line 250).** The single most important function in the file. It
packs the whole world into one JSON object for the browser. Every route ends by calling it.
It has a long docstring explaining both halves — read that.

**Pass 3 — the routes.** Everything decorated with `@app.get` / `@app.post`. They all have
the same shape, so once you've read two you've read all twelve:

```python
@app.post("/api/orders")
async def post_order(req: OrderReq):
    session = SESSION                      # 1. get the session
    require_onboarded(session)             # 2. check preconditions
    ...                                    # 3. do the thing (via sim_engine)
    record(session, "POST", "/api/orders", ...)   # 4. log it for restart recovery
    return {"order": order, "state": snapshot(session)}   # 5. return the WHOLE world
```

### Step 4 — `web/index.html` (74 lines)

The whole page. Plain HTML, no templates. Every element the JS touches has an `id`.
Skim it so the element names in `app.js` mean something.

### Step 5 — `web/app.js` (316 lines) — the browser coordinator

Read `act()` and `render()` first; the rest are helpers they call.

- **`act(method, path, body)`** — every user action goes through here. Sends the request,
  takes the state that comes back, redraws.
- **`render()`** — redraws *everything* from the current state. Called after every change.

Yes, it redraws the whole screen every time. That is deliberate, and at this size it's
instant. Don't optimise it.

### Step 6 — the remaining `web/*.js`

Small, single-purpose, ~70-170 lines each. Read whichever you need:

| File | Job |
|---|---|
| `format.js` | Number formatting + `h()`, a tiny helper for making DOM elements |
| `chart.js` | Draws the SVG price chart |
| `order-ticket.js` | The buy/sell form |
| `safety-net.js` | The "you're down 8%" modal |
| `money-flow.js` | The plain-English sentence under the chart |
| `hint.js` | The little (i) explanation popups |
| `tier-picker.js` | Onboarding card + tier preview |

**Start with `format.js`.** It's 31 lines and defines `h()`, which every other file uses.

## 4. Python idioms that might trip you up

The Python here is terse. These are the patterns that appear most, with their JS equivalents.

**`next(x for x in list if condition)`** — find the first match.
```python
next(t for t in TIERS if t["id"] == tier)      # Python
TIERS.find(t => t.id === tier)                 // JavaScript
```
Difference: Python **throws** if nothing matches; JS returns `undefined`.

**List/dict comprehensions** — build a list by transforming another.
```python
[{"symbol": s, "qty": p["qty"]} for s, p in positions.items()]   # Python
Object.entries(positions).map(([s, p]) => ({symbol: s, qty: p.qty}))   // JavaScript
```

**Multiple assignment in one line**:
```python
session.cash, session.realized = cash, round(session.realized + realized, 2)
```
Two separate assignments. Left-hand names pair with right-hand values in order.

**f-strings** — template literals.
```python
f"Day {day}: bought {qty} shares"      # Python
`Day ${day}: bought ${qty} shares`     // JavaScript
```

**Decorators** — `@app.post("/api/orders")` registers the function below it as a route
handler. Same idea as `app.post('/api/orders', handler)` in Express.

**`dict.get(key)` vs `dict[key]`** — `.get()` returns `None` if missing, `[]` throws.
Like `obj.foo` vs a strict lookup in JS.

## 5. How to run it

```bash
python -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -r server/requirements.txt
python -m uvicorn server.main:app --port 8000
```

Open <http://127.0.0.1:8000>. One process serves both the API and the page.

**Change a `.js` or `.css` file → just refresh the browser.** No build, no restart.
**Change a `.py` file → restart uvicorn** (or add `--reload`).

### Run the tests

```bash
python -m pytest              # 172 tests, about half a second
```

If you see 20 errors about `Client.__init__() got an unexpected keyword argument 'app'`,
your global Python has an old FastAPI. Use the venv — that is what the venv is for.

## 6. Seeing the data with your own eyes

The fastest way to understand the server is to poke it while it's running:

```bash
curl http://127.0.0.1:8000/api/state
```

That is the exact object `app.js` renders from. Every field on screen is in there.

Start a replay and buy something, then look at `/api/state` again:

```bash
curl -X POST http://127.0.0.1:8000/api/onboarding -H "Content-Type: application/json" -d '{"experience":"new","symbol":"HLX"}'
curl -X POST http://127.0.0.1:8000/api/orders -H "Content-Type: application/json" -d '{"symbol":"HLX","side":"BUY","qty":10,"as_of":40}'
```

## 7. Where things live

```
server/
  sim_engine.py     the maths          <- pure, no dependencies, start here
  main.py           the web layer      <- routes, session, snapshot()
  tests/            172 tests
fixtures/*.json     the fake market data
scripts/
  build_fixtures.py generates the fixtures (deterministic - safe to re-run)
web/
  index.html        the page
  app.js            browser coordinator
  *.js              one file per component
  *.json            content: tier rules, coach copy, quiz questions
```

**Content lives in JSON, not in code.** `tiers.json`, `coach.json` and `scenes/act4.json`
hold the words and the rules. Both the server and the browser read them, so the screen and
the server can never disagree about what a tier unlocks. **You can change wording without
touching a `.py` or `.js` file.**

## 8. Things that will surprise you

1. **There's one global session.** `SESSION` is a module-level variable. Two people using
   the same server share a session. That's fine for a demo, wrong for production, and it's
   a known open item.

2. **The server tells the browser when it restarted.** `BOOT_ID` changes on every start. If
   the browser sees a new `BOOT_ID` and has a saved action log, it replays the log to
   rebuild the session. Because the simulation is deterministic, it comes back identical.

3. **Fast-forward moves one day at a time.** Even when you ask for 30 days, the loop steps
   one bar at a time so it can stop the instant a trade fills or a warning fires.

4. **Tests fail the build over *wording*.** `test_content.py` and `test_scenes.py` check the
   copy, not just the code — a missing explanation or a banned word fails CI. That's on
   purpose. If a test complains about your sentence, it is doing its job.

5. **The fixtures are checked for tampering.** `python scripts/build_fixtures.py --check`
   rebuilds them and fails if what's on disk doesn't match. Never hand-edit a fixture.

## 9. Your first change (a safe one)

Change a sentence the user sees, and watch a test catch you if you break a rule:

1. Open `web/coach.json`.
2. Change any `"next"` line under `controls`.
3. Run `python -m pytest server/tests/test_scenes.py -q`.
4. Refresh the browser — no restart needed for a `.json` read by the frontend.

Now deliberately break a rule: put the word `"just "` in one of those lines and re-run the
tests. You'll get a clear failure naming the file, the rule and the fix. Undo it.

That round trip — edit, test, see the guardrail work — is the whole workflow.
